# 📘 **Model Registry — DemandCast**

This document explains how DemandCast manages trained machine-learning models using:

* **MLflow Model Registry** → stores trained models
* **RQ Job IDs** → track background training jobs
* **Supabase `models` table** → records user → model → run_id mapping
* **API endpoints** → retrieve and run predictions

This registry ensures **repeatable predictions**, **version tracking**, **auditability**, and **consistent deployment** across the platform.

---

# 🔹 **1. What Is the Model Registry?**

The *Model Registry* is DemandCast’s system for:

* Storing trained models
* Assigning a unique **run_id** to every trained model
* Keeping track of the model type (demand, stockout, leadtime, pricing, promo, RAG)
* Saving metadata such as:

  * timestamp
  * metrics
  * user_id
  * status of training job

It ensures that each user's model:

* Can be loaded for predictions
* Can be compared against previous versions
* Can be debugged and audited
* Remains accessible even after retraining

DemandCast uses **MLflow** as the underlying model store.

---

# 🔹 **2. Where Models Are Stored**

All trained ML models are stored inside **MLflow** under a run:

```
runs:/<run_id>/model
```

MLflow stores:

* model artifacts (pickle / xgb / keras / sklearn)
* input signature
* metadata
* metrics (MAE, RMSE, F1, etc.)
* parameters

These files are stored in the MLflow artifact store (local folder or S3-backed folder).

---

# 🔹 **3. The Role of `run_id`**

Every training pipeline returns a **unique run_id**, which identifies:

* which model was trained
* which version is stored
* which metrics it achieved
* where its artifacts are located

Example:

```
"run_id": "7ac0dbf47d874300adf99b1c1c12e817"
```

The run_id is used everywhere in DemandCast:

* Dashboard charts
* Prediction endpoints
* Model comparison
* Historical audit
* Automated retraining
* Explanation systems (SHAP, feature importance)

---

# 🔹 **4. How Run IDs Are Generated**

### Training → RQ Worker → MLflow

1. User starts training
2. FastAPI enqueues multiple jobs in RQ
3. RQ worker executes each training function
4. The training function trains a model
5. The pipeline calls `log_*_model_to_mlflow()`, which:

   * registers the model
   * logs metrics
   * saves artifacts
   * returns the **run_id**

Example:

```python
run_id = log_demand_model_to_mlflow(model, "XGBOOST", X_train, y_train, ...)
```

---

# 🔹 **5. How Run IDs Are Saved in Supabase**

The run_id is saved in the **Supabase table `models`** alongside:

* user_id
* model_name
* run_id
* training status
* timestamp

### Example row:

| user_id | model_name | run_id | status | updated_at |
| ------- | ---------- | ------ | ------ | ---------- |
| abc123  | demand     | 7ac0db | queued | 2025-05-01 |

This lets the dashboard fetch each user's latest model.

---

# 🔹 **6. Supabase `models` Table Schema**

```sql
create table models (
    id bigint generated by default as identity primary key,
    user_id uuid not null references auth.users(id),
    model_name text not null,
    run_id text not null,
    status text default 'queued',
    metrics jsonb,
    created_at timestamptz default now(),
    updated_at timestamptz default now()
);
```

### Explanation:

* `id` → internal row id
* `user_id` → links the model to a user
* `model_name` → demand / stockout / pricing / promo / leadtime / rag
* `run_id` → MLflow run identifier
* `status` → training, queued, completed, failed
* `metrics` → optional JSON of results
* `created_at` → training start
* `updated_at` → last update

# 🔹 **7. How Predictions Use the Model Registry**

When a user requests predictions:

### Step 1 → UI asks backend:

```
GET /models/latest?model_name=demand
```

This returns:

```
{
  "run_id": "abc123-run",
  "model_name": "demand",
  "metrics": {...}
}
```

### Step 2 → Backend loads model from MLflow:

```python
model = mlflow.pyfunc.load_model(f"runs:/{run_id}/model")
predictions = model.predict(df)
```

This guarantees:

* consistent results
* reproducible behavior
* correct model versions per user

DemandCast maintains **parallel registries**:

* Demand forecasting

Each has its own:

* separate pipeline

# 🔹 **9. Versioning & Retraining**

Every time training starts:

* A new RQ job is created
* A new MLflow run_id is generated
* A new row is inserted into Supabase
* Model versions accumulate historically

This lets you:

* track performance over time
* revert to older models
* compare versions
* conduct A/B testing

DemandCast does **not overwrite** old models.

---

# 🔹 **10. How Model Status Is Updated**

Status flow:

```
queued → in_progress → completed
             ↓
         failed
```

The worker updates the table automatically using:

```sql
update models set status='completed', metrics=<json> where run_id='<run_id>'
```

This lets dashboards show:

* training progress
* model health
* success/failure

---

# 🔹 **11. Which Model Is “Active”?**

DemandCast considers the **most recent successful run** as the active model for each type.

Query:

```
select * from models 
where model_name='demand' and user_id='<id>' 
order by created_at desc
limit 1;
```

If a model fails, system automatically falls back to the last successful version.

# 📘 **run_id_usage.md**

### *How DemandCast Generates, Stores, Tracks, and Uses Model Run IDs*

---

# 🔹 **1. What is a run_id?**

A **run_id** is a **unique identifier** automatically generated by **MLflow** for every training run.
It is similar to a Git commit hash:

```
run_id = "7ac0dbf47d874300adf99b1c1c12e817"
```

The run_id allows the system to:

* Load specific trained models
* Track model versions
* Perform reproducible predictions
* Link results to the correct training run
* Enable model explainability
* Store model metadata in Supabase
* Manage multiple users' models independently

---

# 🔹 **2. Where is run_id generated?**

The **run_id** is generated inside the MLflow logging function:

```python
run_id = mlflow.start_run().info.run_id
```

Every time a user trains a model, MLflow generates a new run_id stored under:

```
/mlruns/<experiment_id>/<run_id>/
```

The DemandCast pipeline passes this run_id back up to:

* RQ worker
* FastAPI training route
* Supabase table
* UI dashboard

---

# 🔹 **3. Where is run_id stored?**

The run_id is stored in two places:

---

## **A) MLflow Artifact Store**

Location:

```
runs:/<run_id>/model
```

This folder contains:

* Model weights
* Model signature
* Input schema
* Metrics
* Artifacts
* Feature importance
* Preprocessing metadata

---

## **B) Supabase `models` Table**

Each training job stores a record:

| user_id | model_name | run_id | status | metrics |
| ------- | ---------- | ------ | ------ | ------- |

This ensures:

* Users only access their models
* Predictions load the correct version
* Version history is preserved
* Dashboards show correct results

---

# 🔹 **4. run_id in Background Training Jobs (RQ)**

When training starts:

1. FastAPI enqueues a job
2. RQ runs the pipeline
3. Pipeline trains the model
4. MLflow generates run_id
5. run_id returns to worker
6. Worker updates Supabase

### Example:

```python
job = rq_queue.enqueue(run_demand_pipeline, params, token)
```

Inside pipeline:

```python
run_id = log_demand_model_to_mlflow(...)
return run_id
```

Worker:

```
Insert run_id into models table
```

```python
model = mlflow.pyfunc.load_model(f"runs:/{run_id}/model")
```

This guarantees:

* Correct version of model is used

# 📌 **1. Overview**

This document explains **exactly how DemandCast generates predictions** for:

* **Demand Forecasting**
* **Lead Time Prediction**
* **Stockout Prediction**
* **Price Elasticity & Revenue Curves**

Predictions in DemandCast follow a **strict, consistent, and secure pipeline**:

```
uploaded data → preprocessing → feature generation →
MLflow model loading → model inference → post-processing → UI response
```

Everything is tied to a **run_id**, ensuring:

* reproducibility
* version control

# 🔹 **2. Flow of Prediction Requests**

Every prediction triggered by the front-end follows this consistent flow:

```
(1) User selects/run model → 
(2) Frontend calls backend with model_name →
(3) Backend fetches latest run_id from Supabase →
(4) Backend loads model from MLflow →
(5) Backend preprocesses latest uploaded files →
(6) Backend generates features → 
(7) Model predicts →
(8) Results returned to frontend UI
```

This architecture ensures that **predictions always match the user’s latest trained model**.

Predictions rely on the user’s uploaded files, stored in Supabase:

* `sales`

* `products`
* `promotions`
* `supplier/leadtime`

These are retrieved by:

```
retrieve_files(token) → DataFrames
```

This ensures the model always predicts based on:

* user-specific datasets
* latest uploaded versions
* cleaned & sanitized DataFrames

Example:

* prediction data matches training schema

Example row:

| ------- | ---------- | ------ | ------ | ------- |

* order → delivery pairs
* supplier reliability scores
* historical lead times
* variability features

* expected lead time in days

Output:

```
sku_id, supplier_id, expected_leadtime, delay_probability
```

Use cases:

* reorder point calculation
