# 🔷 **4. Shared Flow for All Prediction Routes**

Every predict endpoint runs this universal function:

```
def predict(model_name, token):
    user_id = get_user_id(token)
    run_id = get_latest_run_id(user_id, model_name)
    model = mlflow.load(run_id)
    dfs = retrieve_files(token)
    X = build_features(dfs)
    preds = model.predict(X)
    result = postprocess(preds)
    return JSON
```

# 📘 **demand_pipeline.md**

### *Demand Forecasting Pipeline – Full Technical Documentation for DemandCast*

---

# 🔷 **1. Overview**

The **Demand Forecast Pipeline** in DemandCast predicts **future product demand** using historical sales, pricing, promotions, and product attributes. The pipeline is designed to be:

✔ Automated
✔ Scalable
✔ MLflow-tracked
✔ Feature-rich
✔ Fully reproducible
✔ Per-user isolated

It runs asynchronously via **Redis + RQ** and returns an **MLflow run_id**, which is later used for predictions, dashboards, SHAP explainability, and decision support.

---

# 🔷 **2. Pipeline Objectives**

The Demand Forecast pipeline determines:

* **Future sales quantity** for each SKU at each location
* **Forecast horizon** (7/14/30/90 days)
* **Promotion-sensitive demand patterns**
* **Seasonality patterns**
* **Trend shifts**
* **Price elasticity effects** (if pricing data found)

It enables downstream tasks like:

* Stock planning
* Replenishment triggers
* Safety stock computation
* Promo planning
* Revenue forecasting

---

# 🔷 **3. Input Requirements**

The pipeline expects (at minimum):

### **Sales File (`sales_df`)**

Required columns:

* `date`
* `product_id`
* `sales`
* `price` *(optional but improves accuracy)*

Optional but useful:

* `location_id`
* `promo_flag`
* `customer_id`

If the user does not upload `products_df`, DemandCast automatically generates one from unique product_ids.

---

# 🔷 **4. Pipeline Steps**

The pipeline consists of **8 major steps**, each described below.

---

# 🔷 **STEP 1 — Column Mapping**

DemandCast supports arbitrary column names.

Using the synonym mapper:

```
date_col_syn
product_id_col_syn
sales_col_syn
price_col_syn
```

The pipeline auto-detects correct columns like:

| Uploaded Column | Mapped As  |
| --------------- | ---------- |
| sale_date       | date       |
| sku             | product_id |
| qty_sold        | sales      |
| unit_price      | price      |

This allows users to upload any dataset without renaming columns.

---

# 🔷 **STEP 2 — Preprocessing**

Performed by `preprocess_data()`:

* missing date handling
* sorting by date
* converting categorical to numeric
* removing extreme outliers
* normalizing negative/unrealistic sales
* removing constant columns
* forward-fill price gaps
* unify date format

Goal: **clean, fully aligned dataset ready for feature extraction.**

---

# 🔷 **STEP 3 — Feature Engineering**

Performed by `extract_demand_forecast_features()`.

Features include:

### **Lag features**

```
lag_1, lag_3, lag_7, lag_14, lag_30
```

### **Rolling windows**

```
rolling_7_mean
rolling_14_mean
rolling_30_mean
rolling_7_sum
rolling_30_sum
```

### **Seasonality features**

```
day_of_week
month
week_of_year
is_weekend
```

### **Price features**

```
price
price_change
discount_percent
price_rolling_mean
```

### **Promo features (if promo flag exists)**

```
is_promo
promo_lag_7
promo_rolling_sum_30
```

### **Trend features**

```
sales_diff
rolling_slope
```

Hundreds of features may be generated depending on data availability.

---

# 🔷 **STEP 4 — Train–Test Split (Time Series)**

DemandCast uses a **chronological split**:

```
70% → Train
15% → Validation
15% → Test
```

Unlike random splits, time-series split ensures:

* no leakage
* realistic future prediction simulation

Done via `train_test_split_time_from_xy()`.

---

# 🔷 **STEP 5 — Class Imbalance Handling**

*(Not for demand — but built-in for future hybrid classification tasks)*

Demand forecasting is **regression**, so imbalance handling is not needed, but the pipeline includes hooks for potential hybrid tasks, such as:

* demand=0 vs demand>0
* new SKU warming

---

# 🔷 **STEP 6 — Auto Model Selection & Training**

Performed by `train_demand_forecast_model()`.

Model is chosen based on dataset size:

| Dataset Size                  | Model                                     |
| ----------------------------- | ----------------------------------------- |
| Small (<10k rows)             | Prophet or RandomForest                   |
| Medium (10k–150k)             | XGBoost                                   |
| Large (>150k)                 | LSTM                                      |
| Very large & time-series rich | TFT (disabled for now → fallback to LSTM) |

### **Models Supported**

* **Prophet**
* **Random Forest Regressor**
* **XGBoost**
* **LSTM** *(TensorFlow)*
* (TFT to be added later)

Pipeline trains only **one** model — not a brute-force ensemble.

---

# 🔷 **STEP 7 — MLflow Logging**

The trained model is logged into MLflow:

* parameters used
* metrics (MAE, RMSE, R²)
* feature importance
* model pickle / saved model
* plots & artifacts
* environment info

Returns a unique:

```
run_id  →  "7abfa272018f4e179d"
```

This ID is stored in Supabase so predictions can be fetched later.

---

# 🔷 **STEP 8 — Prediction From Logged Model**

After logging, the pipeline validates model loading:

```
preds, proba = predict_from_demand_mlflow_run(run_id, X_test)
```

Outputs:

* test predictions
* probability metrics (for LSTM/Prophet)
* time-series forecast values

Ensures the pipeline is reproducible via MLflow.

# 📘 **leadtime_pipeline.md**

### *Lead Time Prediction Pipeline – Technical Documentation for DemandCast*

---

# 🔷 **1. Overview**

The **Lead Time Pipeline** in DemandCast predicts:

* **Supplier Delivery Lead Time**
* **Lead Time Variability**
* **Delivery Delays**
* **Supplier Performance Patterns**
* **Future expected lead time for reordering decisions**

It is essential for:

* Replenishment planning
* Safety stock calculation
* Supplier risk assessment
* Automated reorder point (ROP) modeling

---

# 🔷 **2. Objective of Lead Time Modeling**

The goal is to compute:

### **1️⃣ Predicted Lead Time**

Expected number of days from order to delivery.

### **2️⃣ Lead Time Variability**

Standard deviation of lead time; important for safety stock.

### **3️⃣ Supplier Reliability**

Probability of on-time delivery based on past behavior.

### **4️⃣ Anomaly Detection** (Optional)

Spotting outlier delays or disruptions.

DemandCast uses lead time predictions inside the larger **Demand → Inventory → Stockout** flows to automate replenishment decisions.

---

# 🔷 **3. Input Requirements**

The pipeline expects a **supplier/PO (Purchase Order)** dataset with at least:

### **Mandatory columns**

* `order_date`
* `delivery_date`
* `product_id`
* `supplier_id`

### **Optional but recommended**

* `order_quantity`
* `received_quantity`
* `price`
* `po_id`
* `location_id`

If date columns have irregular names (e.g., `po_dte`, `delv_dt`), DemandCast auto-maps them using the synonym dictionary:

```
order_date_col_syn
delivery_date_col_syn
product_id_col_syn
supplier_col_syn
```

---

# 🔷 **4. Pipeline Steps**

The Lead Time Pipeline consists of **8 steps**:

---

# 🔷 **STEP 1 — Column Mapping**

DemandCast automatically detects & renames:

| Detected Column         | Standard Name |
| ----------------------- | ------------- |
| dt_ordered, order_d     | order_date    |
| dt_delivered, recv_date | delivery_date |
| sku, item               | product_id    |
| vend_id, supplier       | supplier_id   |

This works via:

```
map_column(df, order_date_col_syn)
```

---

# 🔷 **STEP 2 — Lead Time Calculation**

A new column is created:

```
lead_time = (delivery_date - order_date).days
```

Invalid rows are removed:

* negative lead times
* unrealistically large values
* missing dates

---

# 🔷 **STEP 3 — Preprocessing**

Performed by `preprocess_data()`:

* remove duplicates
* convert date → datetime
* standardize supplier_name
* fix inconsistent product_ids
* drop nulls
* ensure numeric types

---

# 🔷 **STEP 4 — Feature Engineering**

Performed using:

```
extract_leadtime_features(df)
```

### **Base Features**

* `lead_time` (target)
* `order_quantity`
* `supplier_id`
* `product_id`

### **Date Features**

* `order_month`
* `order_week`
* `order_dayofweek`
* `is_month_start`
* `is_month_end`

### **Supplier Features**

* `avg_lead_time_supplier`
* `std_lead_time_supplier`
* `supplier_delay_rate`
  (% deliveries delayed)

### **Product Features**

* `avg_lt_product`
* `volatility_product_lt`

### **Trend Features**

* rolling windows:

```
rolling_mean_7_lt
rolling_std_30_lt
rolling_slope_lt
```

### **Optional Parameters Integrated**

From UI:

#### ✔ **Smoothing Window (lookback)**

Smooths historical lead times:

```
rolling_mean(smoothing)
```

#### ✔ **Supplier Variability Handling**

If `variability = True`:

* additional volatility features
* weighted sample variance
* supplier reliability score

These parameters now directly affect model training.

---

# 🔷 **STEP 5 — Train–Test Split**

Performed using:

```
train_test_split_time_from_xy()
```

Split is chronological:

| Set        | Portion |
| ---------- | ------- |
| Train      | 70%     |
| Validation | 15%     |
| Test       | 15%     |

This avoids leakage and preserves time dependency.

---

# 🔷 **STEP 6 — Auto Model Selection & Training**

Performed by:

```
train_leadtime_model_auto()
```

### ✔ Model is chosen based on:

* number of rows
* number of categorical features
* smoothing and variability effects
* dataset density

### Model Decision Logic

| Condition                 | Model               |
| ------------------------- | ------------------- |
| many categorical features | CatBoost            |
| < 20k rows                | Linear Regression   |
| < 200k rows               | Random Forest       |
| 200k–2M rows              | LightGBM            |
| > 2M rows                 | XGBoost (hist tree) |
| fallback                  | Random Forest       |

### Incorporating UI Parameters

**1️⃣ Smoothing (`smoothing=int`)**

Applied during feature creation:

* moving averages
* volatility banding
* rolling-window adjusted lead time

**2️⃣ Variability Handling (`variability=bool`)**

If True:

* extra volatility features
* supplier reliability weighting
* penalization for high-variance suppliers
* risk-adjusted RMSE loss scoring

### Output of training:

* selected model type
* trained model object
* metrics (MAE, RMSE, R²)

```
uplift_revenue = units_sold*promo_price - baseline_sales*regular_price

```
